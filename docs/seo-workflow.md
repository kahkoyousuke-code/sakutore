# Search Console を見て対策を立てる手順

`.claude/agents/seo-analyst.md`（SEO担当エージェント）と、人が手で回すときの両方で使う手順書。
**この文書が唯一の正本**で、エージェント側の定義はここを読みに来るだけにしてある。
手順を変えるときはここを直す。

コラムを1本追加する作業そのものは `CLAUDE.md` の「コラム記事を追加するときの手順」が正本。
この文書は「次にどの記事を書くか／どの記事のどこを直すか」を決めるところまで。

**先に `CLAUDE.md` の「このサイトのゴール」を読むこと。** 何が効いて何が効かないかの実測が
載っている。技術的な SEO はすでに整っていて、課題は順位と CTR。

---

## 0. 実行の全体像

```
Search Console からデータを取る（npm run seo:fetch）
  → レポートを出す（npm run seo:report）
  → セクションごとに打ち手を決める
  → 直せるところをコードに反映する（title/description・本文・新しい記事）
  → lint / tsc / build で検証
  → ブランチを切って PR を出す（master には直接 push しない）
```

**master に直接 push しない。** 何を公開するかは必ず人がマージで判断する。

---

## 1. データの入り口をつくる

2通りある。**A が用意できるならそちらにする**（前期間との比較とインデックス状況まで出せる。
定期実行にも載せられる）。B は認証情報なしで今すぐ動かしたいとき用。

### A. サービスアカウントで API から取る（推奨・初回だけ設定が要る）

1. [Google Cloud Console](https://console.cloud.google.com/) でプロジェクトを作る（既存のものでよい）
2. 「APIとサービス」→「ライブラリ」で **Google Search Console API** を有効にする
3. 「認証情報」→「認証情報を作成」→ **サービスアカウント** を作る。
   ロールは付けなくてよい（権限は Search Console 側で渡す）
4. できたサービスアカウントの「キー」タブ →「鍵を追加」→ **JSON** をダウンロード
5. [Search Console](https://search.google.com/search-console) → 対象プロパティ →
   設定 →「ユーザーと権限」→「ユーザーを追加」で、**鍵 JSON の `client_email`**
   （`...@....iam.gserviceaccount.com`）を **権限「制限付き」** で追加する。
   読み取りしかしないので所有者にはしない
6. 鍵を環境変数に入れる。改行が壊れやすいので base64 で渡すのが安全

   ```bash
   # 手元で確認するとき
   export GSC_SERVICE_ACCOUNT_JSON="$(base64 -w0 /path/to/key.json)"
   export GSC_SITE_URL="https://sakutore.jp/"   # ドメインプロパティなら sc-domain:sakutore.jp
   npm run seo:fetch
   ```

   クラウド実行環境や CI では、同じ2つを環境変数（シークレット）として設定する。

- **鍵をリポジトリに置かない。** `.gsc/` と `.env.local` は `.gitignore` 済み
- 取得結果は `.gsc/latest.json`（と日付つきのコピー）。これも git 管理外

### B. 画面からエクスポートした CSV を使う

1. Search Console →「検索パフォーマンス」→ 期間を選ぶ（既定は過去3か月）
2. 右上の「エクスポート」→「CSV をダウンロード」（zip が落ちてくる）
3. zip を展開して、中の `クエリ.csv` `ページ.csv` を `.gsc/csv/` に置く

   ```bash
   mkdir -p .gsc/csv && unzip -o ~/Downloads/*.zip -d .gsc/csv
   npm run seo:report
   ```

この経路は1期間ぶんしか入っていないので、**前期間との比較（レポートの4・5）は出ない**。
インデックス状況も URL 検査 API を使わない簡易版になる。

## 2. レポートを出す

```bash
npm run seo:fetch     # A の経路のときだけ。B なら飛ばす
npm run seo:report
```

`npm run seo:report -- --out .gsc/report.md` でファイルに書ける（`.gsc/` は git 管理外）。

判定の基準値の既定は `scripts/seo-config.mjs` の `DEFAULT_THRESHOLDS`。サイトの規模が変わって
「該当なし」ばかり／多すぎになったら、`seo.config.mjs` の `thresholds` で上書きする
（一部だけ書けば、書いたところだけ差し替わる）。

---

## 3. レポートの読み方と打ち手

レポートのセクション番号と、触るファイルの対応。**上から順に効きやすい**（0が一番手前）。

| セクション | 意味 | 打ち手 | 触るファイル |
|---|---|---|---|
| 1. あと一歩のクエリ | 5.5〜20位。内容はあるが決め手が足りない | 該当記事に節を足す。既存記事からそのページへ内部リンクを張る | `src/app/column/<slug>/page.tsx` |
| 2. 順位のわりにクリックされていない | 検索結果に出ているのに選ばれていない | `pageMetadata()` の `title` / `description` を書き直す | `src/app/column/<slug>/page.tsx` |
| 3-1. 記事はあるが届いていない | 需要はあるが20位より下 | 該当記事に加筆 | `src/app/column/<slug>/page.tsx` |
| 3-2. 受け皿になる記事が無い | 流入はあるが扱っている記事が無い | ネタ帳に候補を足す（**書く前に競合の混雑度を見る**） | `docs/column-backlog.md` |
| 4. 落ちているページ | 前期間比でクリックが減った | 順位が下がったのか表示ごと減ったのかを分ける（下記） | 判断による |
| 5. 伸びているクエリ | 需要が増えている方向 | その方向に次の記事を寄せる | `docs/column-backlog.md` |
| 6. インデックス状況 | 登録されていない URL | GSC の URL 検査から登録をリクエスト（**人の作業**） | なし |

**このサイトで効くのは 1・2・3-2 の3つだけ**（`CLAUDE.md` の「このサイトのゴール」の実測）。
なかでも 2 は CTR 0.7% という現状からして一番安く効く。

### セクション4の分け方

- **順位だけ下がった**（表示回数はある）→ 競合に内容で負けている。本文の追記・表の追加
- **表示回数ごと減った** → 検索需要そのものが減ったか、検索意図が変わった。
  季節性（年始のダイエット需要など）なら触らない
- **今期間に消えた**（クリック0）→ インデックスから外れた疑い。セクション6と突き合わせる

### やらないこと

- **数字が小さいうちに動かさない。** 表示回数が2桁前半のクエリは偶然で上下する。
  `THRESHOLDS` の下限はそのための足切りで、下げると振り回される
- **キーワードを詰め込まない。** タイトルに同じ語を並べる、本文に不自然に語を足すのは逆効果
- **記事を量産して薄くしない。** 切り口が既存記事と被るなら足さない
- **クエリの混雑度を見ずに書かない。** 同じ型で書いた2本が 10.5位 と 24.7位 に割れた実例が
  `docs/column-backlog.md` にある。差は書き方ではなくクエリ側の混雑度だった

## 4. 直すときのルール

### title / description を書き換えるとき

- **直すのは `src/app/column/<slug>/page.tsx` の `pageMetadata()`。** 直書きしない
- `title` は 32文字前後まで。検索結果で切られる。`- サクトレ` の手前が本体なので、
  クエリに当たる語は**前半**に置く
- `description` は 80〜120字。記事で答える具体的な論点を入れる（「〜を解説します」だけにしない）
- 記事一覧（`src/app/column/page.tsx`）の `title` / `description` も揃えるかは内容で判断する

### 本文に加筆するとき

`CLAUDE.md` の「コラム記事を追加するときの手順」と「絶対に守るルール：数字とプロフィールの
単一ソース」が正本。**数字を書く前に `src/lib/` に該当モジュールがあるか探すこと。**
既存37本と食い違う数字を書かない。

### 新しい記事を立てるとき

1. **先に競合の混雑度を見る**（`docs/column-backlog.md` の「どれを先に書くかの基準」）
2. `docs/column-backlog.md` に候補として足す
3. 書いたら `src/app/column/page.tsx` の一覧に追記（忘れると内部リンクが張られない）
4. `seo.config.mjs` の `keywords` にその記事のキーワードを足す

レポートのクエリをそのまま記事のテーマにしない。クエリは検索窓に打たれた言葉で、
記事としては狭すぎたり広すぎたりする。

## 5. 検証する

```bash
npm run lint && npx tsc --noEmit && npm run build
```

3つとも通ること。テストは無いので、`build` が通ることと dev server での目視が検証。

## 6. PR を出す

```bash
git switch -c seo/<短い説明>
git add -A
git commit
git push -u origin seo/<短い説明>
```

- `.gsc/` は git 管理外なので、コミットに入らないことを `git status` で確認する
- **main へ直接 push しない**
- PR 本文に入れるもの
  - どのセクションの、どの数字を見て直したのか（表示回数・順位・CTR を具体的に）
  - 触ったファイルと、変更の前後
  - 検証コマンドの結果
  - **判断を人に渡す部分**（インデックス登録のリクエストなど、コードで完結しないもの）

数字は再現できないので（`.gsc/` はコミットしない）、**根拠になった数字は PR 本文に転記する**。
これをしないと、後からマージの可否を判断できない。

## 7. 定期実行

スケジュール実行からこの文書を読ませる想定。頻度の目安は **月1回**。Search Console のデータは日々ぶれるので、週次で見ると数字を追いかけて
本質的でない手直しを繰り返すことになる。

定期実行では次の順で回す。

1. `npm run seo:fetch && npm run seo:report`
2. レポートのセクション1・2・3 から、**その回で手を入れるのは3件まで**に絞る
3. 直して検証して PR を1本にまとめる
4. セクション6の「インデックス登録のリクエスト」は人の作業なので、PR 本文に箇条書きで残す

## 8. 他のプロジェクトで使う

この仕組みはサクトレ専用ではない。サイトごとに違うところは `seo.config.mjs` に
まとめてあり、`scripts/` の3ファイルはどのサイトでもそのまま動く。
姉妹サービス（サクサプ・サクメシ）にも同じやり方で入れられる。

### 持っていくもの

| ファイル | 触るか |
|---|---|
| `scripts/gsc-fetch.mjs` | そのままコピー |
| `scripts/seo-report.mjs` | そのままコピー |
| `scripts/seo-config.mjs` | そのままコピー（既定値と設定ローダー） |
| `seo.config.mjs` | **書き直す**（下記） |
| `package.json` | `seo:fetch` / `seo:report` の2行を足す |
| `.gitignore` | `.gsc/` を足す |
| `.claude/agents/seo-analyst.md` | 参照先のファイル名をそのサイトに合わせる |

Search Console 側の設定（サービスアカウントの追加）はプロパティごとに要る。
Google Cloud のプロジェクトと鍵は使い回してよく、**各プロパティの
「ユーザーと権限」に同じ `client_email` を足すだけ**でよい。

### `seo.config.mjs` の書き方

すべて任意。書かなかった項目は既定値になり、`seo.config.mjs` 自体が無くても
Search Console のデータだけでレポートは出る（ページの突き合わせが要る
セクションが簡略版になる）。まず設定なしで動かし、物足りないところを足すのが早い。

```js
export default {
  // 対象プロパティ。--site と $GSC_SITE_URL のほうが優先される
  siteUrl: 'https://example.com/',

  // 公開済みページ。配列でも、配列を返す関数でもよい
  // path はサイト内の絶対パス。title / description があると
  // 「クリックされていないページ」で今の文面も一緒に出る
  pages: () => [{ path: '/blog/foo', title: '…', description: '…', date: '2026-01-01' }],

  // クエリにこの語が含まれたら、そのページが扱っているとみなす
  keywords: () => [{ kw: 'プロテイン', path: '/blog/foo' }],

  // まだ作っていないページの企画
  planned: () => [{ id: 'bar', title: '…' }],

  // URL 検査にかけるパス。省略すると pages の path
  inspectPaths: () => ['/', '/blog', '/blog/foo'],

  // クエリと企画の突き合わせで無視する一般語（そのジャンルで誰でも使う語）
  stopWords: ['効果', '選び方', 'おすすめ'],

  // 基準値の上書き。書いたところだけ差し替わる
  thresholds: { nearTop: { minImpressions: 10 } },

  // 打ち手の文面。そのサイトのファイル構成に合わせる
  advice: { lowCtr: '`content/posts/*.md` の front matter を見直す。' },
}
```

`pages` などを関数にしておくと、実行のたびにソースを読み直すので、記事を足しても
設定を触らずに済む。サクトレの `seo.config.mjs` は `src/app/column/` のディレクトリと各記事ページの
`pageMetadata()` を正規表現で読んでいる（一覧ファイルが無く、TypeScript を
そのまま実行できないため）。Markdown で記事を持つサイトなら
front matter を読む関数にすればよい。

### サイトによって変わりやすいところ

- **`stopWords`** — ジャンルの一般語。サプリなら「サプリ」「効果」、
  筋トレなら「筋トレ」「トレーニング」。ここを入れないと、企画の突き合わせが
  ほぼ全部に当たって役に立たなくなる
- **`thresholds`** — 記事が少ないうちは `minImpressions` を下げないと
  「該当なし」ばかりになる。逆に流入が増えたら上げる
- **`advice`** — 「どのファイルを直すか」はサイトごとに違う。ここを書いておくと、
  レポートを読んだ人（エージェント）が迷わない
