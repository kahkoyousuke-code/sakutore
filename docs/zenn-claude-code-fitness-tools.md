筋トレ歴15年、フィジークの大会で入賞したことがあります。本業はエンジニアではありません。

そんな人間が Claude Code で筋トレサイト [サクトレ](https://sakutore.jp) を作り、いま51ページまで育ちました。AIメニュー診断、RM計算機、カロリー計算機、適正重量チェッカー、種目の動画一覧、コラム21本。

この記事では、**AIを使った個人開発で一番効いた設計判断**と、**まだ全然うまくいっていないこと**を正直に書きます。技術的な結論を先に書くと、こうです。

> **「AIで作る」の勝負どころは、LLMをどこに使うかではなく、どこに使わないかを決めるところにあった。**

## 作ったもの

| ツール | 中身 |
|---|---|
| メニュー診断 | 5問に答えるとその日のメニューが出る（LLM使用） |
| AIチャット | 筋トレの質問に答える（LLM使用） |
| RM計算機 | 「80kg×5回」から1RMを換算（**LLM不使用**） |
| カロリー計算機 | 基礎代謝と目標カロリーを算出（**LLM不使用**） |
| 適正重量チェッカー | 目的別の推奨重量を出す（**LLM不使用**） |

スタックは Next.js 14（App Router）+ TypeScript + Tailwind + Vercel。LLMは Claude Haiku 4.5 を Anthropic SDK 経由で叩いています。

## 1. 計算できるものをLLMにやらせない

AIで個人開発をしていると、全部LLMに投げたくなります。実際、最初はRM計算機も「AIに聞けばいいのでは」と思っていました。

やめました。1RMの換算はただの式だからです。

```ts
// Epley式。これで終わり
function calcEpley(weight: number, reps: number) {
  const oneRM = reps === 1 ? weight : weight * (1 + reps / 30);
  // ...
}
```

これをLLMにやらせると、こうなります。

- 遅い（数百msが数秒になる）
- 金がかかる（1リクエストごとに課金）
- **たまに間違える**（これが致命的）

3つ目が本質です。**確定的な答えがある処理をLLMに通すと、確定性を失うだけで何も得ない。** 筋トレの重量は体に直接かかる数字なので、間違った値を出すのは実害が出ます。

一方、メニュー生成は違います。「30分・自宅・ダンベルのみ・初心者・胸を鍛えたい」から適切な5種目を選ぶのは、正解がひとつに定まりません。ここは**LLMが圧倒的に強い領域**です。

境界線はここに引きました。

> **式で書けるならコードで書く。「妥当な組み合わせ」を選ぶ必要があるならLLMに任せる。**

副次的な効果として、**LLMが落ちてもサイトの大半は動きます**。計算機3つはクライアントサイドで完結しているので、Anthropic APIが死んでもユーザーは困りません。全部LLMに寄せていたら、API障害＝全機能停止でした。

## 2. ドメイン知識をプロンプトのルールに落とす

ここが15年やってきたことが効いた部分です。

筋肉には**超回復**という仕組みがあり、鍛えた部位は48〜72時間の回復を必要とします。昨日胸をやった人に今日また胸を出すメニューは、トレーナーとしては失格です。

なので、ブラウザに保存してあるトレーニング履歴から「部位ごとに何日前にやったか」を組み立てて、プロンプトに差し込んでいます。

```ts
function recoveryLine(recovery?: RecoveryInfo[]): string {
  if (!Array.isArray(recovery) || recovery.length === 0) return "";
  const parts = recovery.map((r) => {
    if (r.daysSince === null) return `${r.group}=未実施`;
    if (r.daysSince === 0) return `${r.group}=本日実施済み`;
    return `${r.group}=${r.daysSince}日前`;
  });
  return `\n部位別の回復状況:${parts.join(" / ")}`;
}
```

生成されるプロンプトの一部はこうなります。

```
部位別の回復状況:胸=1日前 / 背中=4日前 / 脚=未実施

設計ルール:
- 回復済み(2日以上空いている/未実施)の部位を優先し、本日や前日に実施した部位は避ける
```

たったこれだけですが、出力の質がはっきり変わりました。「今日は何をやるべきか」という問いに対して、**履歴を踏まえた答え**が返ってくるようになります。

ここで言いたいのは、**プロンプトエンジニアリングの正体は、多くの場合ドメイン知識の言語化だ**ということです。「48〜72時間の回復が必要」という知識を持っているかどうかが、そのまま出力の差になりました。テクニックではなく、知っているかどうかでした。

AIで個人開発をするなら、**自分が10年やってきた何か**を題材にするのが一番強いと思います。プロンプトに書ける知識の量で差がつくからです。

## 3. LLMのJSON出力を、落ちない前提で扱わない

メニュー生成はJSONで受け取っています。ここは素直に書くと本番で壊れます。

やったことは4つです。

**① SDKの自動リトライを切って、自分で制御する**

```ts
const client = new Anthropic({ timeout: 20 * 1000, maxRetries: 0 });
```

`maxRetries: 0` にして、リトライは自前で1回だけ。SDK任せにすると、ユーザーが待たされている間に裏で何度も再試行されて、体感がひたすら遅くなります。**ユーザーを待たせている処理のリトライ回数は、自分で握るべき**でした。

**② 途中で切れたレスポンスを検出する**

```ts
if (message.stop_reason !== "end_turn") {
  throw new Error(`レスポンスが途中で切れました (stop_reason: ${message.stop_reason})`);
}
```

`max_tokens` に達して切れたJSONは、当然パースに失敗します。これを「JSONパースエラー」として処理すると原因がわからなくなるので、**切れたのか壊れたのかを分けて**扱います。

**③ エラーをSDKの型で分類して、日本語に翻訳する**

```ts
if (error instanceof Anthropic.APIConnectionError) {
  return { message: "AIサービスに接続できませんでした。通信環境を確認してください。", status: 503 };
}
if (error instanceof Anthropic.RateLimitError) {
  return { message: "リクエストが集中しています。しばらく待ってからお試しください。", status: 429 };
}
```

Anthropic SDKはエラーを型で投げ分けてくれるので、**それぞれに対して「ユーザーが次に何をすればいいか」を書いた日本語**を返します。「エラーが発生しました」だけの画面は、ユーザーにとって何の情報でもありません。

**④ モデルは Haiku 4.5**

短いJSONを吐かせるだけの用途に、上位モデルは要りませんでした。速くて安いほうが、この用途では純粋に上位互換です。**モデル選定は「一番賢いのを選ぶ」ではなく「タスクに足りる中で一番速いのを選ぶ」**でした。

## 4. 正直に書く：ここまでやって、検索流入はほぼゼロです

ここからが、この記事で一番書きたかったことかもしれません。

51ページ作りました。sitemap.xml も canonical も OGP も内部リンクも整えました。Lighthouse も回しました。**技術的には、たぶん満点に近いです。**

**それでも Google のインデックス登録はほぼゼロです。**

Search Console を見ると、URLは検出されている（Discovered = 41）のに、登録されない（Indexed ≈ 0）。URL検査にかけると「クロールされていません」と出ます。**評価されて落とされたのではなく、そもそも見に来られていない。**

理由ははっきりしていて、**新規ドメインで、被リンクがゼロだから**です。Googleにはクロールの予算があり、誰からもリンクされていない無名のサイトは、その予算を割り当ててもらえません。

これはコードでは直せませんでした。sitemapを直しても、metadataを完璧にしても、**「知られていない」という問題はコードの外側にあります。** ここ数ヶ月で一番の学びは、たぶんこれです。

> **動くものを作る能力と、見つけてもらう能力は、別のスキルだった。**

AdSenseにも2回落ちました。理由は「有用性の低いコンテンツ」。これも痛いけど納得していて、コラムを20本書いたものの、**中身が「誰でも書ける一般論」だった**からです。15年の実体験も、大会に出た話も、記事には1行も入っていませんでした。AIに書かせると、平均的で、無難で、誰の記憶にも残らないものが出てきます。それを20本並べても、Googleから見れば価値はゼロでした。

いま直しているのはそこです。例えば[BIG3の重量目安の記事](https://sakutore.jp/column/strength-standards)では、一般的な目安表を出したうえで、**自分の実際の数字（開始時は3種目とも60kg、ベストはベンチ120・スクワット120・デッド160）が目安表とどうズレたか**を書きました。ベンチとスクワットが同じ120kgで止まっているのは、目安表から見れば明確に「バランスが悪い」です。でもフィジークは上半身で評価される競技なので、それでよかった。**この話は、私にしか書けません。**

## まとめ

Claude Code で個人開発をしてみて、効いた判断はこの3つでした。

1. **式で書けるものはコードで書く。**LLMは「正解が定まらない選択」にだけ使う。確定的な処理をLLMに通すと、確定性を失うだけで得るものがない
2. **プロンプトの質は、ドメイン知識の量で決まる。**自分が長くやってきた領域を題材にすると、テクニックなしで差がつく
3. **LLMのレスポンスは壊れる前提で扱う。**リトライを自分で握り、切れたのか壊れたのかを分け、エラーはユーザーの次の行動に翻訳する

そして、コードでは解決できなかったこと。

4. **作れても、見つけてもらえない。**これはコードの外側の問題で、いま一番苦戦しています

同じように「AIで作れるようになったけど、誰にも見られていない」という人、たぶんかなりいると思います。もし何か突破口を見つけた人がいたら、教えてください。
